# 本次 Session 討論紀錄：新計畫的契約、文件分工與錯誤處理

日期：2026-09-30（Asia/Taipei）

## 起點與文件分工

**問：專案當時是否完全沒有 Design by Contract 規範？**

答：不是。當時的 `README.md` 已有「下一版公開方法契約」，列出 `GameController` 的方法、輸入、輸出、DTO 與預期錯誤；但契約、遊戲規則和玩家流程混在同一份文件，而且那個介面尚未實作。

**問：使用者希望各 Markdown 文件負責什麼？**

答：`technical_spec.md` 只管 C# 的變數名稱、類別與方法寫法，現有內容已符合要求；`design_by_contract.md` 管 `use_case.md` 所列流程的輸入與輸出；`project_structure.md` 管專案與物件放置方式，WinForms 不必細分太多資料夾，並參考 `SnakeEatFood2`；`exceptional_spec.md` 管錯誤類型及依類型設置 `try/catch`；`README.md` 改名為 `use_case.md`。原 `refact_plan.md` 所述 Core／Application／WinForms 目標架構當時尚未實作。

## 當時提供的選項與使用者選擇

**問：`design_by_contract.md` 要以什麼粒度描述 input／output？**

提供的選項：

1. **Use case＋公開方法（建議）**：每個玩家流程列輸入與可見結果，再對應公開方法的前置／後置條件。
2. **只按 use case**：聚焦玩家操作與畫面結果，不固定方法簽章。
3. **只按公開方法**：延續原有 `GameController` 表格，由 use case 文件保留玩家流程。

使用者選擇：**Use case＋公開方法**。後來使用者要求新計畫擺脫現有程式，因此「固定公開方法簽章」這部分已撤回；目前有效的契約只固定 use case 的輸入、可觀察輸出與狀態保證。

**問：參考 `SnakeEatFood2` 的平坦結構，要簡化到什麼程度？**

提供的選項：

1. **保留分層、減少資料夾（建議）**：保留 Core／Application／WinForms 專案，各專案內只在必要時建資料夾。
2. **合併為單一 WinForms 專案**：遊戲、控制器與表單放同一主專案，較接近參考專案。
3. **保留原改造計畫**：維持 Core／Application／WinForms 分層與預定檔案安排。

使用者選擇：**合併為單一 WinForms 專案**。測試專案維持獨立；目前仍只是新計畫，尚未修改 C# 專案。

**問：`exceptional_spec.md` 的 `try/catch` 政策偏好哪一種？**

提供的選項：

1. **只捕捉可處理錯誤（建議）**：正常遊戲結果用回傳值／狀態，在 UI 邊界依可恢復例外類型處理。
2. **每個 use case 都捕捉**：每條操作流程各自包 `try/catch`。
3. **集中在最外層捕捉**：UI 事件共用一個錯誤處理入口。

使用者選擇：**每個 use case 都捕捉**。後續規格將其落在各 UI 操作入口，依錯誤類型處理；正常遊戲結果不當作例外。

**問：單一 WinForms 專案下，原 `GameController` 方法與 DTO 簽章如何處理？**

提供的選項：

1. **保留簽章（建議）**：保留 `Start`、`Replay`、`Tick`、`Hit`、`GetState` 與 DTO 契約，只改所在專案及文件。
2. **重新設計簽章**：依各 use case 的輸入輸出重新設計方法與型別。
3. **不規定程式介面**：文件只固定玩家可觀察行為，方法由實作時決定。

使用者選擇：**重新設計簽章**。後來進一步要求新計畫不沿用現有程式，因此目前文件尚未固定新的簽章或 DTO 結構。

**問：各 use case 捕捉到可預期例外時，UI 如何處理？**

提供的選項：

1. **就地提示並維持狀態（建議）**：在該操作顯示可理解訊息，錯誤不得造成部分計分或狀態變更。
2. **僅記錄，不提示**：寫入紀錄並讓玩家繼續。
3. **提示後重置遊戲**：顯示錯誤並回到第一關初始狀態。

使用者選擇：**就地提示並維持狀態**；此保證針對已定義、可預期的輸入錯誤。未知故障另依後面的選擇停止本局，不假設狀態一定完整。

**問：這輪是否只整理文件，暫不修改 C#？**

提供的選項：

1. **只整理文件（建議）**：建立責任明確的規格文件、更新引用，程式另行處理。
2. **文件與程式一起改**：同一實作計畫包含單一 WinForms 專案重構。

使用者選擇：**只整理文件**。

**問：重新設計公開方法時，偏好哪種操作模型？**

提供的選項：

1. **依玩家動作命名（建議）**：開始關卡、點擊洞口、重玩、時間推進有明確操作，直接提供更新後狀態。
2. **依各關 use case 命名**：第一關開始、第二關開始、各關點擊等分別有方法。
3. **單一命令入口**：傳入操作種類與資料，由單一方法回傳統一結果。

使用者選擇：**依玩家動作命名**。目前文件保留「開始關卡、點擊洞口、時間推進、重玩、讀取狀態」所需能力，但不固定方法名稱。

**問：錯誤類型採哪種設計？**

提供的選項：

1. **標準例外＋少量自訂（建議）**：非法參數用 .NET 標準例外，只有需單獨恢復的遊戲錯誤才新增自訂型別。
2. **只用 .NET 標準例外**：以 `ArgumentException`、`InvalidOperationException` 等分流。
3. **每個 use case 自訂例外**：各流程各有專屬類型。

使用者選擇：**標準例外＋少量自訂**。目前唯一明確的非法洞口輸入使用 `ArgumentOutOfRangeException`；沒有具體需求的自訂例外，因此暫不新增。

**問：玩家操作完成後如何提供最新狀態？**

提供的選項：

1. **直接回傳狀態（建議）**：開始、重玩、時間推進提供最新狀態，點擊另提供是否命中。
2. **操作後再讀狀態**：操作只回傳必要結果，UI 另行讀取狀態。
3. **只用事件推送**：控制器在狀態變更時發事件。

使用者選擇：**直接回傳狀態**。目前保留「操作後能取得最新狀態與命中結果」的能力要求，具體回傳型別與傳遞方式尚未固定。

**問：在不適用階段再次開始或重玩，應如何處理？**

提供的選項：

1. **正常忽略並回傳現況（建議）**：遊戲不變，UI 仍可取得目前狀態。
2. **視為操作錯誤並擲例外**：以自訂例外通知 UI。

使用者選擇：**正常忽略並回傳現況**。目前文件固定「不改變狀態、可觀察現況、不擲預期例外」，未固定回傳型別。

**問：未列入契約的程式或環境例外要怎麼處理？**

提供的選項：

1. **顯示錯誤並停止本局（建議）**：保留資料，停止計時與後續操作。
2. **顯示錯誤並允許繼續**：玩家可重試，但一致性較難保證。
3. **不捕捉未知故障**：交由 WinForms 預設錯誤機制處理。

使用者選擇：**顯示錯誤並停止本局**。

## 實作、修正與目前結論

**問：使用者要求實作當時的計畫後，實際改了什麼？**

答：將 `README.md` 改為 `use_case.md`，新增 `design_by_contract.md`、`exceptional_spec.md`、`project_structure.md`，移除與新結構衝突的 `refact_plan.md`，更新 `AGENTS.md`，並將舊 `plan.md` 標為歷史執行計畫。只修改文件，沒有修改 C#。當時的第一版 `design_by_contract.md` 曾固定 `GameController` 簽章、`GameStateDto` 等名稱及 DTO 欄位。

**問：使用者後來對契約提出什麼修正？**

答：使用者指出這是**擺脫現有程式的新計畫**，不應先固定 DTO 欄位細節。依此修正 `design_by_contract.md`，移除固定的方法簽章、DTO 欄位和列舉名稱；同時修正 `project_structure.md` 與 `exceptional_spec.md` 對舊型別的依賴。`project_structure.md` 現在只定義單一 WinForms 主專案、獨立測試專案與責任界線，不把舊類別逐一搬移當成預設方案。

**問：目前是否至少已固定 DTO 名稱，只是還沒固定欄位？**

答：**沒有。**目前連 DTO 名稱也未固定；是否使用 DTO、DTO 的名稱與欄位，都留待後續介面設計。`design_by_contract.md` 目前只固定 use case 的輸入、可觀察輸出、狀態保證與必要的操作能力。

**問：本次 session 的文件驗證與程式狀態如何？**

答：根目錄 Markdown 連結與 `git diff --check` 已檢查通過。新規格仍是待實作計畫；本 session 未改動 C#，也未執行建置或程式測試。
