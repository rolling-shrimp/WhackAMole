### Q6. 後續目標與命中後的新目標，何時出現？

使用者選擇：從首個目標出現起，每 700 毫秒更換一次。

每個目標最多有效 700 毫秒；被提早命中後先消失，仍等原定更換時刻，不能立即補出新目標。時間更新延遲時也不能延長舊目標期限或替過期目標補計分。

滿 700 毫秒的舊目標不能命中。原定時刻產生的新目標是另一個目標，依自己的有效期限判斷，不與舊目標混為同一次命中。

### Q7. 計分、關卡截止及重玩有哪些保證？

原有遊戲規則持續適用：

- 第一關灰色老鼠加 1 分，結算時達 42 分過關。
- 第二關灰色老鼠加 1 分、棕色倉鼠加 3 分、炸彈扣 2 分，分數最低為 0；結算時達 52 分闖關成功。
- 命中有效目標增加對應紀錄，目標消失且同一目標只能計分一次。炸彈命中前分數為 0，仍是正常命中。
- 每關獨立計時 60 秒，滿 60 秒先結算，不再產生目標或接受命中；達分數門檻不提前結算。
- `HitHole` 先驗證洞口，再同步到點擊時的遊戲時間。回傳 `false` 仍可能伴隨時間到期造成的正常階段轉換。
- 第一關失敗或第二關結束後可重玩。重玩清除兩關全部紀錄，立即重新開始第一關的 60 秒計時，並重新隨機決定首個目標時機。

### 補充問答

#### Q13. 原本 exceptional_spec.md 定義哪些 throw exception 型別？

原本明確指定主動拋出的型別只有 `ArgumentOutOfRangeException` 與 `InvalidOperationException`：前者處理非法洞口與關卡編號，後者處理非法結算及畫面前置階段違約。正常未命中、正常到期及不適用階段的開始或重玩不拋例外；未知故障保留原型別，由 UI 的 `catch (Exception)` 處理。

#### Q14. 原本有 Output 違約的例外嗎？當時如何歸類？

沒有專門的分類或指定型別，也未明定檢查責任及時機。若錯誤結果以例外回報，當時會落入「未知程式或環境故障」，停止本局；但 `catch` 不會自動發現錯誤 output，必須有實際檢查。

討論例子包括 `GetLevelState(1)` 卻產生第二關資料、分數小於 0，以及 `FinishLevel()` 執行後仍允許本關命中。最後一例即使回傳 `void`，仍違反後置保證。

| --- | --- | --- |
| Input 範圍違約。 | `ArgumentOutOfRangeException`。 | 拒絕呼叫方傳入的非法編號，在變更前驗證，保留原狀。 |
| 前置階段違約。 | `InvalidOperationException`。 | 拒絕不允許階段的結算或畫面操作，在變更前驗證，保留原狀。 |
| Output／後置條件違約。 | `OutputContractViolationException`，專案自訂，直接繼承 `Exception`。 | 方法未完成自己承諾的結果，屬已辨識的實作缺陷；UI 停止本局，不保證已完成的部分變更回復。 |
| 未知程式或環境故障。 | 保留原例外型別。 | 仍由最後的 `catch (Exception)` 處理，停止本局。 |

### 確認的責任與保證

- 檢查範圍包含回傳值的語意、範圍與內容，以及執行後的遊戲狀態或畫面；九份 `void` 合約同樣有後置條件須保證。
- 由擁有該合約的方法在回傳或正常完成前檢查，包括正常未命中與不適用階段正常忽略的路徑；以 `design_by_contract.md` 的既有保證為準，不新增 DTO 欄位或未約定的限制。
- Output 違約的診斷內容須指出合約方法、違反的保證與實際結果；呼叫方不得補值、修正結果或用假結果繼續流程。
- 所有十五份合約的對應 UI 入口均須在 `catch (Exception)` 前捕捉 `OutputContractViolationException`，涵蓋該入口完整流程內呼叫的合約。捕捉後先停用計時器及玩家輸入，再顯示「遊戲發生錯誤，本局已停止」，保留資料與畫面供診斷，不自動重玩。
- 時間來源、亂數來源或 UI 操作本身拋出的未知例外保留原型別，不一律改包成 Output 違約。Input／前置階段違約的「原狀不變」保證不擴張至 Output 違約。

#### Q20. 每份合約的共同驗收標準有哪些？

- Input 限制及 output 語意與範圍符合合約。
- 正常操作達成分數、紀錄、目標、計時與關卡階段的後置保證。
- 正常忽略、正常未命中及擲出例外依各合約分別判定；合約要求保持原狀時，確認資料或畫面未變更。
- 驗證 700 毫秒、60 秒、第一關 41／42 分、第二關 51／52 分，以及炸彈扣分最低為 0 等邊界。
- 畫面合約驗證玩家實際可見的結果，並確認不修改遊戲資料或自行推進時間。
- 指定時間及隨機情境可以重現；首個目標立即與延後 700 毫秒兩種允許結果分別驗收，不設定特定機率比例，也不要求有限次數的隨機執行必定觀察到所有結果。
- 同一目標不可重複計分；提早命中仍等原定更換時刻，延遲更新不得延長舊目標期限。700 毫秒時產生的新目標依自己的有效期限判定。
- 輸出／後置保證違約與未知故障的停止及診斷依例外規範驗收，不把保持原狀的保證擴張至所有故障。

#### Q21. void 或回傳 false 的合約，要怎麼判定通過？

`void` 合約以執行後的遊戲狀態或畫面保證驗收。例如結算後停止目標並保存正確結果，畫面操作後呈現正確資訊。

`HitHole` 回傳 `true` 時，除回傳值外，也驗證計分、紀錄與目標失效。回傳 `false` 時，仍依合約驗證是否發生正常時間推進或關卡結束，不能一律要求所有狀態完全未變更。

非法洞口則須在時間更新及計分前拒絕，並保持遊戲狀態不變。讀取關卡狀態及畫面呈現均不自行推進時間。
